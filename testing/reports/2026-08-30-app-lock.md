What is covered beyond the wording of the scenarios:

- LOCK-002 checks that with free-length input the screen does not leave by itself
  on the fourth digit of a six-digit code;
- LOCK-004 checks that after a change to a shorter code the unlock screen has
  re-read the length and waits for four dots rather than six;
- LOCK-005 separately checks cancelling at the code prompt and a wrong code: the
  protection stays on in both cases;
- LOCK-006 separately checks cancelling at each of the two confirmations - the
  data and the code are intact afterwards;
- LOCK-007 checks the opposite case too: a return sooner than a minute does not
  ask for the code.

### How LOCK-007 tells a timeout from a cold start

`launchApp` in Maestro brings the process up anew, and the lock screen would
simply appear as it does on a cold start. So the return from the background is
done by tapping the icon on the springboard, and the sign of a surviving process
is the screen: before backgrounding, the app is left on the journal, and after
the code is entered it stays there instead of opening Home.

## Defects found

### 1. The app content stays in the accessibility tree behind the lock screen

Severity: Major (privacy), the priority is assigned by the product owner.

The lock screen is an opaque overlay above the Stack, and visually it covers
everything: the screenshot `lock-002-cold-start-locked.png` shows no content. But
in the accessibility tree the elements underneath remain visible:

```
{'accessibilityText': 'Начать молитву'}
{'accessibilityText': 'История молитв', 'resource-id': 'journal-button'}
{'accessibilityText': 'Настройки',      'resource-id': 'settings-button'}
{'resource-id': 'lock-screen'}
```

Reproduction:

1. enable the PIN, restart the app, wait for the lock screen;
2. `maestro --device <UDID> hierarchy` - under the `lock-screen` node the
   elements of the hidden screen are listed.

The touches are genuinely intercepted by the overlay: a tap on the coordinates of
`journal-button` with the lock on leads nowhere - checked separately. The risk is
not in the touches but in VoiceOver: it walks the accessibility tree and
activates elements directly, bypassing hit testing, which means that with
VoiceOver on a locked app can be both read out and swiped through. The overlays
have no `accessibilityViewIsModal` / `importantForAccessibility`.

A side effect for the automated tests: assertions on the text of a hidden screen
pass while the lock is on, so in the flows the precondition "the protection is
off" is checked with an explicit `assertNotVisible: id: lock-screen` rather than
by the presence of a button on Home.

The fix requires a product and architectural decision (VoiceOver is part of the
behaviour of the protection), so the app was not changed.

### 2. A tap that lands as a screen appears does not reach the handler

Severity: Minor.

The first tap after a cold start and the first tap on a code entry overlay that
has just appeared are lost. Observed on three different elements:

- "Начать молитву" on Home right after the launch - reproduces consistently;
- "Забыли пин-код?" right after the lock screen appears;
- "Отмена" right after the code entry overlay appears (`pin-prompt-cancel`).

The second tap always works. The behaviour is not new and is not tied to the
lock: the existing `ios-stage03-navigation.yaml` already works around it with a
`doubleTapOn`. For a person this is a rare case (one has to land within the
220-320 ms of the appearance animation), for the automated tests it is a source
of flakiness, so the flows have repeated taps under `runFlow: when:`.

## Notes filed without a defect

- **`lib/lock.ts` has no unit tests at all.** `npm test` gives 86/86, exactly as
  many as before the feature. Meanwhile the module has pure functions ready for
  tests: `shouldLockAfterBackground` (the 60-second boundary), `isValidPin` (the
  4 and 8 digit boundaries), the parsing of the length and the "an incomplete
  record means the protection is off" rule in `readLockConfig`. Precisely those
  boundaries are not covered by automated tests right now: the 60 seconds are
  only verified by an end-to-end scenario on the simulator, which takes more than
  a minute of real time.
- `npm run typecheck` - exit 0.
- `testing/e2e/ios-smoke-full.yaml` is red in this environment at the moment, and
  that is unrelated to the lock: it fails on `hideKeyboard`, which closes the
  prayer setup sheet together with the keyboard and returns to Home. In the new
  flows the keyboard is closed with the "Done" button. Fixing the smoke is a
  separate task.

## Manual checks

These could not be automated; each needs a person with a device.

**LOCK-008, the privacy screen.** The snapshot of the app in the task switcher is
taken by the system, and neither Maestro nor `simctl` gives it up.

1. Enable the PIN in the settings, open a journal with records.
2. Swipe up (or double-press Home) to open the app switcher.
3. The app card should show the privacy screen - the lamp and the name - and not
   the journal.
4. Return to the app sooner than a minute: the code is not requested, the journal
   is where it was.

**LOCK-009, biometrics.** In the simulator no samples are enrolled, so the
`biometrics-toggle` is not displayed - this is expected and confirmed: the
"Protection" section shows only the PIN and the code change.

1. On a device with Face ID / Touch ID configured, enable the PIN.
2. Make sure the biometrics toggle appeared only after the PIN was enabled.
3. Turn it on: the system should ask for a confirmation, and only after a success
   should the toggle stay on.
4. Restart the app: the Face ID prompt should appear by itself, once.
5. Cancel the system prompt - the PIN entry should remain, and there must be no
   endless repeated prompt.

**LOCK-010, the samples removed after enabling.** Turn biometrics on, then delete
Face ID in the system settings. The lock screen must not offer biometrics, and
entry by code must work.

## Retest after the fixes (later the same day)

Defect 1 is fixed (ClickUp `86cbbqzce`): the overlays (`privacy-curtain`,
`lock-screen`, `pin-prompt`) received `accessibilityViewIsModal`.
`maestro hierarchy` on a locked screen no longer shows content elements; the PIN
pad and "Забыли пин-код?" remain in the tree. The solution is iOS-only; the
Android equivalent was moved to `86cbbr2ad` and needs a decision from the owner.

Defect 2 - the cause was clarified (`86cbbqzcj`): it is not the animation but the
dev LogBox banner over the bottom strip of the screen - the first tap dismisses
the banner instead of pressing. The source of the warnings on the home screen (a
deprecated Skia API in `components/Flame.tsx`) was removed; another warning,
apparently a native one, surfaces along the prayer flow, so a repeated "На
главную" tap under `runFlow: when:` was added to
`ios-lock-006-forgot-pin-prepare.yaml`. Release builds have no LogBox, so the
symptom is dev-only.

The note about the unit tests is closed (`86cbbqzcr`): the pure logic was moved
into `lib/lockPolicy.ts`, `npm test` gives 104/104. The smoke was fixed
(`86cbbqzcp`): 39/39 steps.

The final run of the whole LOCK-001 to LOCK-007 series in a row is green (007 is
automated as described above). The manual LOCK-008 to LOCK-010 remain to be
checked on a device.

Manual checks on a device (2026-08-31, the owner's iPhone): the PIN works;
LOCK-009 failed at first - the Face ID toggle silently refused to turn on (a
build without `NSFaceIDUsageDescription`, `86cbbru2t`: `ios/` had not been
re-synced after the change to `app.json`, and the code swallowed the error
without any feedback). After an `expo prebuild`, a rebuild and a fix that
distinguishes a cancellation from an error - **LOCK-009 passed**, Face ID works.
